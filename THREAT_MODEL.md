# Threat model

This repository holds the `st0x-alpaca` library, the typed boundary between st0x services and Alpaca, and the Alpaca gateway (`t0-alpaca`, `s01-alpaca`), a service that runs the library with one Alpaca credential on behalf of bots and operators. Neither owns balances or runs business workflows, but a wrong wire value can place an order, conversion, journal, withdrawal, mint, or redemption with the wrong asset or amount, and a leaked credential can do the same directly.

## Library trust boundaries and assets

- Consumer domain values cross into JSON requests sent to Alpaca.
- Alpaca JSON responses cross into validated Rust types.
- Credentials (Basic key pair, KMS signed or locally signed JWT assertions, bearer tokens) cross into HTTP headers.
- The `mock` feature runs local HTTP servers and, for the tokenization mock, sends onchain ERC-20 transfers from a test wallet. It is for test suites only.

The protected assets are equity quantities, USD cash and prices, USDC conversion and transfer amounts, symbol and network routing, idempotency keys, Travel Rule beneficiary identity, and API credentials.

## Library threats and controls

| Threat | Concrete risk | Control (where) |
| --- | --- | --- |
| Spoofing | A request is sent without the configured identity, or credentials reach a host the operator did not configure. | Every client attaches credentials through the crate-private `AuthRuntime` (`auth.rs`). Base and token URLs must be HTTPS, or HTTP on a loopback host, with no embedded credentials, query, or fragment (`endpoint.rs`; issuer, broker, wallet, and tokenization clients; `AuthRuntime::build`). The corporate-action stream sends credentials only to `stream.data.alpaca.markets` over HTTPS and rejects embedded credentials and fragments (its query carries the stream filter); a development loopback endpoint is credential-free. Issuer request URLs are built on the configured origin from percent-encoded path segments, and empty or dot segments are rejected, so an identifier cannot redirect a credentialed request to another host or endpoint (`endpoint::resolve_segments`). The issuer, broker, wallet, tokenization, corporate-action stream, and token-mint HTTP clients do not follow redirects. `KmsJwtAuth` and `AuthRuntime` cannot be built with arbitrary URLs or HTTP clients from outside the crate. |
| Tampering | Invalid amounts or routing values reach Alpaca, or malformed responses reach consumers. | Order quantities and journal quantities are `Positive<FractionalShares>`; limit prices use `AlpacaLimitPrice` precision rules; withdrawals take `Positive<Usdc>`; USD-to-USDC buys use a whole-cent `notional` and USDC sells a 6-decimal `qty`. Alpaca crypto amounts keep the raw value for cash valuation and expose only the value floored to 6 decimals (`AlpacaAmount`). Responses are checked for symbol mismatch (positions, quotes), required fields per order status (`IncompleteOrder`), filled-quantity mismatch, crossed or non-positive quotes, calendar date mismatch, network mismatch on tokenization requests, and response id mismatch on issuer polls. The issuer redeem call refuses a network that is not on the ITN network list before any HTTP call (today every `Network` value is on the list, so this is a guard against a future variant). |
| Repudiation | A retried mutation cannot be reconciled with what Alpaca executed. | Caller supplied idempotency keys are sent unchanged for orders, conversions, and mints: `client_order_id` for orders and conversions, and `Idempotency-Key` plus `client_request_id` for mints. A redeem derives a stable 36 character UUIDv5 `Idempotency-Key` from `issuer_request_id` under an operation specific namespace. A duplicate `client_order_id` adopts the existing order; keyed lookups (`orders:by_client_order_id`, mint recovery by issuer request id, redemption by tx hash) recover a lost response. A stalled conversion reports how the cancel was answered instead of claiming a result. |
| Information disclosure | Credentials, tokens, private keys, or Travel Rule identity appear in logs or errors. | `Debug` for `AlpacaAuth`, `AlpacaBrokerApiCtx`, the clients, the token cache, and the signer redacts secrets; credential header values are marked sensitive. Wallet response bodies have `beneficiary_entity_name` redacted in trace logs and `ApiError` messages, and a body that cannot be redacted is omitted (fail closed). Error bodies from KMS and the token endpoint are truncated to 512 bytes; a successful mint's token is never put in an error or log. Note: trace-level logs include full broker and market-data response bodies, which contain account balances; consumers must treat trace logs as sensitive. |
| Denial of service | A malformed value panics, or a retry or poll never ends. | No `unwrap` or `expect` outside tests (Clippy denies them). Retries are limited to classified transient errors: the issuer policy retries at most 5 times with jittered backoff; the wallet transfer and deposit status polls retry every transient read (a read error `AlpacaWalletError::permanence()` classifies Transient: a 5xx, 408, or 429, a transport failure, a token mint failure that is not deterministic, a retryable gateway hop) up to their attempt cap (`PollingConfig::max_retries`, 10 by default, per read), and the transfer tx hash poll retries every transient read with no attempt cap until its deadline. The conversion, tokenization, wallet transfer, deposit, and transfer tx hash polls wait for the longer of their own interval or backoff and `Retry-After`. No read starts at or after the poll deadline, and a read still running there is dropped. Every poll loop is bounded: conversion orders (300 s, then cancel and a 30 s settle window), wallet transfers (30 min), tokenization requests (`PollingConfig` timeout), account activities (1000 pages and a repeated token check). The SSE decoder caps a frame at 64 KiB and releases the buffer on a poison frame. Broker, market data, tokenization, issuer, and token mint requests have connect and request timeouts. Direct wallet requests have a 10 second connect timeout and no total request timeout, because a timed out keyless withdrawal may still have reached Alpaca and must never invite an automatic retry. The gateway constructs its wallet client with a 30 second total request timeout to bound detached work, but expiry remains an ambiguous result that requires reconciliation. The gateway cuts the whitelist read of a withdrawal, whitelist removal, or Travel Rule patch at the operation deadline. Rate limits from the broker, market data, wallet, tokenization, and issuer clients surface as `Backpressure` with the `Retry-After` hint so the consumer can back off; the corporate action stream reports a 429 as `RateLimited { retry_after }` with Alpaca's `Retry-After` hint, and the consumer reconnect loop backs off, as in issuance. |
| Elevation of privilege | A feature surface gains access to unrelated integrations, or a caller withdraws to an address that is not an approved whitelist entry. | Features are additive and each compiles alone. The `wallet` feature includes account administration: `create_whitelist_entry`, `delete_whitelist_entry`, `patch_whitelist_travel_rule`, `remove_whitelist_entries`, and `patch_all_whitelist_travel_rules` change the account's withdrawal whitelist, so any consumer built with `wallet` can add, remove, or change withdrawal destinations. `initiate_withdrawal` withdraws only to an address that Alpaca reports as an approved whitelist entry for the asset (`check_withdrawal_whitelist`), so a new entry cannot receive funds before Alpaca approves it. `submit_withdrawal` is the raw withdrawal POST without that check: its caller must run `check_withdrawal_whitelist`, and any destination rule of its own, before calling it, as the gateway's `wallet.withdraw` does. |

## Gateway

The gateway (`crates/gateway`, built to run as Cloud Run services `t0-alpaca` and `s01-alpaca`, one per account, see [docs/gateway.md](docs/gateway.md)) adds one trust boundary: callers to the gateway. Bot runtimes are to call it on Cloud Run with a Google ID token; humans call it through IAP on a load balancer. Everything a caller sends (token, path, query, body, `X-On-Behalf-Of`) is untrusted until the gateway has checked it. Behind the gateway, the library boundaries above apply unchanged. The gateway adds these protected assets: the broker credential it signs with, the binding to one account, the pinned destinations, and the audit stream.

The gateway is the target credential boundary, not the current one. The controls below hold for traffic that goes through the gateway. Until liquidity and issuance switch their transport to the gateway ([RAI-1935](https://linear.app/makeitrain/issue/RAI-1935), [RAI-1936](https://linear.app/makeitrain/issue/RAI-1936)) and their direct credentials are removed ([RAI-1938](https://linear.app/makeitrain/issue/RAI-1938)), the bots keep calling Alpaca directly with their own credentials, outside every gateway control, and the Cloud Run, IAP, KMS key, and audit sink setup named below exists only once the private infrastructure is deployed.

| Threat | Concrete risk | Control (where) |
| --- | --- | --- |
| Spoofing | A caller acts on a tier it does not hold, or a token minted for another service is accepted. | Each tier verifies its own identity (`crates/gateway/src/auth.rs`). Bot ID tokens: signature against Google's keys, issuer, audience `identity.bot_audience`, and `sub` in `identity.bot_principals`. Human IAP assertions: signature, issuer, and the audience of their own backend, so a read assertion never opens the write tier. Outside the app, Cloud Run `run.invoker` admits only the bot service accounts and the IAP service agent, and the load balancer routes only the two human prefixes. |
| Tampering | A caller steers a mutation to another account, host, or destination, or smuggles path segments into an Alpaca URL. | No request names an account or an Alpaca URL: the account id, the account number, and every pinned address live only in the reviewed config, which refuses unknown keys outside `[broker]` (`crates/gateway/src/config.rs`). Startup reads the account from Alpaca and refuses to serve unless it is ACTIVE and reports `expected_account_number` (`crates/gateway/src/state.rs`). Bot withdrawals go only to `wallet.bot_withdrawal_destinations` and human withdrawals never to them (`check_withdrawal_destination`), journals go only to a configured counterparty (`counterparty_account`), and mints go only to `tokenization.mint_recipients` (`crates/gateway/src/handlers`); an empty list allows nothing, and an empty `wallet.bot_withdrawal_destinations` answers the bot's withdrawals `403 capability_disabled` while human withdrawals keep serving. Symbols are ASCII letters, digits, `.`, `/`, and `-` with no empty, `.`, or `..` part (`crates/gateway-api/src/dto/mod.rs`), and the library percent encodes each symbol where it enters a URL. Request bodies refuse unknown fields. Order keys must have the form of the caller's tier: bare UUIDs for bots, `cli-` prefixed UUIDs for humans. |
| Repudiation | A mutation cannot be tied to the caller who asked for it or to what Alpaca did. | Every request on an operation's route writes an audit record, including a request refused for its credential (caller `unverified`), its bot subject, or a body, path, or query that does not parse, with the caller, tier, operation, key, reason, request digest, money moving fields, Alpaca status (on a success the last Alpaca answer's, on a failure its own), the `X-Request-ID` of the Alpaca responses (`alpacaRequestIds`), the Alpaca object id, outcome, and error code. Each caller supplied value the record keeps (key, reason, money moving fields, `X-On-Behalf-Of`) is cut to its first 256 characters, and symbols, journal counterparties, assets, and networks have wire length bounds; the request digest covers the whole request. The record keeps the first 100 Alpaca request ids, each cut to 128 characters. The work of every call runs on a detached task that writes the record carrying its real result, also when the gateway answered the caller without it (its deadline, shutdown) or the caller went away (`crates/gateway/src/state.rs`, `crates/gateway/src/audit.rs`, `crates/gateway-api/src/record.rs`). Human mutations need a non blank `reason`. The audit stream is routed to a protected audit destination. |
| Information disclosure | Credentials, tokens, or Travel Rule identity leak through the audit stream. | Audit records never carry credentials, tokens, Travel Rule names, or response bodies. With `environment = "production"`, or with the `[broker]` mode set to the production Broker API in any environment, config validation accepts only the Cloud KMS credential (`client_id` and `kms_key_version`) (`crates/gateway/src/config.rs`), so a credential that reaches the real money endpoint is a KMS key that only the runtime service account can sign with, and no key material lives in its config or the image. A staging deployment against the sandbox accepts only the Basic key pair, which then sits in that deployment's mounted config, since the wallet and tokenization clients mint KMS tokens at the production token endpoint. Validation refuses the local private key in every environment, since those clients cannot sign with it. The Travel Rule beneficiary comes from config, never from a request. A config that does not parse is reported with the parser's message only, never the offending line, so a malformed credential line stays out of the startup log and the `--validate-config` output (`ConfigError::Parse`). |
| Denial of service | Operator scripts spend the credential's Alpaca rate limit that the bots need, or one request holds the gateway. | The read and write tiers share `human_budget_per_minute`, counted in calls (`crates/gateway/src/budget.rs`): each human call takes one unit, except the keyed reads that client poll loops repeat, and a human `activities.list` reads at most 10 pages. Bots are never charged. The budget is per process. The broker, wallet, each tokenization client, the three issuer clients, and the corporate action stream client each build an independent credential token cache, mint lock, and `Retry-After` hold, so a hold one client takes does not stop its siblings in that process or any client in another process. Cloud Run runs the old and the new revision side by side during a rollout and while the old one drains, so `human_budget_per_minute` is half the human share and a new revision is deployed with no traffic, then takes all of it at once ([docs/gateway.md](docs/gateway.md#rollouts)). Human `activities.list` needs a non blank `types`. Every call answers by its own deadline (`Operation::deadline`) while its work runs detached under a send gate that closes at that deadline, at shutdown, and before the caller is answered without the result. The library asks the gate before each credential mint starts and as each Alpaca API request would leave, so a request is either in flight before the `outcome_unknown` answer, which covers it as one that may still land, or held back: no Alpaca API request and no new credential mint starts after that answer (`AppState::run`, `st0x_alpaca::request_id::gated`). A credential mint already in flight may finish (at most three 10 second round trips), and the request it was minted for is then held back. A withdrawal, whitelist removal, or Travel Rule patch also cuts its whitelist read at that deadline, so a stalled read ends the work. |
| Elevation of privilege | A reader or a bot reaches an operation outside its tier, or a switched off operation still runs. | An operation is mounted on a tier only when the profile's capability matrix lists it (`crates/gateway-api/src/ops.rs`, `crates/gateway/src/routes.rs`); readers have no mutation routes. `disabled_operations` answers `403 capability_disabled` without a new image. Bot `orders.recover`, `orders.find`, and `conversions.find` accept only bot keys, so the bot never adopts a human order as its own. |
| Elevation of privilege (profile) | A deployment serves another account's operations, or a caller other than issuance reaches the issuer calls. | `profile` is required config; it names the deployment in every audit record and picks the capability matrix (`Operation::tiers`). `t0` serves no issuer or stream operation. On `s01` the bot tier serves only `issuer.mint_callback`, `issuer.redeem`, `issuer.request`, and `corporate_actions.stream`, and no human tier serves the issuer POSTs. Each deployment's `bot_principals` and `run.invoker` admit only its own bot: liquidity on `t0-alpaca`, issuance on `s01-alpaca`. |
| Tampering and repudiation (issuer) | An issuer POST that may have reached Alpaca is reported as not applied, or the stream relay sends the credential elsewhere or alters what Alpaca sent. | The issuer calls run the library unchanged against the configured account; `clientId` names the issuance participant and selects no account. Issuer bodies and the `issuer.request` path refuse a blank, overlong, or control bearing request id, a symbol outside the shared rule, and a redeem quantity that is not a positive plain decimal with at most 9 fractional digits (`crates/gateway-api/src/dto/issuer.rs`). The redeem `Idempotency-Key` is a stable 36 character UUIDv5 derived from the complete issuer request id, so spaces, Unicode, and longer identifiers never produce a malformed header. The library reports whether any attempt of an issuer POST may have been written (`IssuerCallError`), and once it may, the answer and its audit record are `outcome_unknown` with the last Alpaca status, also when a resend was refused (`crates/gateway/src/answer.rs`). Every issuer answer and record takes its Alpaca status from the last answer Alpaca gave (`IssuerCallError::alpaca_status`), so a hold the client keeps locally names none. Mint callbacks, redemptions and `issuer.request` use separate issuer clients, so a `Retry-After` hold on one does not stall the others. The stream client sends the credential only to `stream.data.alpaca.markets` over HTTPS, and a deployed build refuses a loopback stream URL (`CorporateActionsConfig::endpoint` in `crates/gateway/src/config.rs`, checked by `--validate-config` and at startup); the gateway's tests serve the stream from a loopback mock that requires the credential (`authenticated_loopback`). The relay forwards Alpaca's bytes unchanged, decodes nothing, and is served on the `s01` bot tier only; it has no deadline and ends after `corporate_actions.idle_timeout_secs` without a chunk, at the Cloud Run request timeout, or when shutdown starts. A connect still pending at shutdown answers unavailable while its tracked task keeps the remaining grace. A stream 429 is `CorporateActionStreamError::RateLimited { retry_after }`, relayed as `backpressure` with Alpaca's `Retry-After`. Each connect writes one result audit record, plus an unavailable answer record when shutdown answers first. |

Residual risks:

- The Broker API credential belongs to the broker firm, not to the T0 account. The gateway pins one account, but whoever can sign with the KMS key can act on every account of the firm. Only the runtime service account holds `signerVerifier` on the key, KMS Data Access logging records every signature, and revoking the BrokerDash credential stops all its traffic at Alpaca.
- Detached work is cut at shutdown, and otherwise runs until its last Alpaca request answers or reaches its finite timeout. On SIGTERM every call in flight answers at once without its result and starts no further Alpaca API request or credential mint. Broker API requests and wallet requests built by the gateway each have a 30 second total timeout. This bounds local work but does not prove that Alpaca rejected a request whose answer timed out.
- Keyless mutations that are not idempotent are never resent automatically. Withdrawals, journals, and whitelist creation carry an `operationId` for the audit record only, because Alpaca does not dedupe them. After `outcome_unknown`, the caller waits for the record that carries the work result: `answered` with Alpaca traffic when the work returned while the handler waited, or `settled` when the handler had already answered without it. Shutdown can cut the task before either result record exists. A local timeout and one empty recovery read never prove that Alpaca did not apply the mutation. Before any new withdrawal, reconcile repeatedly over a window longer than the local timeout and expected Alpaca processing delay, and match the amount, destination, and a transfer `created_at` no earlier than the gateway answer. Before any new journal, apply the same rule to its quantity, symbol, destination, and `created_at`. Whitelist creation recovery checks the intended address and asset for the same longer window. Any replacement after no match is a deliberate operator decision, never an automatic retry.
- During a rollout or a platform replacement of the instance, two gateway processes serve at once. The half budget rule keeps their human admissions within the human share, but each broker, wallet, and tokenization client has its own credential mint `Retry-After` hold. A hold one client takes does not stop its siblings in that process or any client in the other process.
- Whitelist removal and Travel Rule patching have no Alpaca key either, but every attempt drives the whitelist to the same end state, so their `outcome_unknown` answer carries `retryableWithSameKey: true` and the same request may be resent unchanged. A loop that stops after its first write names the entries it had already changed in its message and its audit record; an answer at its deadline or at shutdown names none, and the operator reads `wallet.whitelist`.
- The library resends an issuer POST after a transport failure or a 5xx, as issuance's direct calls do today, and Alpaca's dedupe on `tokenizationRequestId` is not established, so one mint callback may reach Alpaca more than once. A redeem derives a stable UUIDv5 `Idempotency-Key` from its `issuerRequestId`, so Alpaca replays the first answer to a resend with the same body; a reused `issuerRequestId` without a replay answers 422, which the gateway answers as `outcome_unknown`. The gateway does not widen this: it retries nothing itself and answers `outcome_unknown` without `retryableWithSameKey`, and issuance keeps its own handling (the callback job's retry, `AlpacaCallFailed` and recovery through `issuer.request`).

## Required evidence

- Request bodies preserve Alpaca's string encodings without rounding: exact issuer redeem `qty`, order `qty` and `notional`, journal `qty`, withdrawal amount (unit tests in each module).
- Credential tests: insecure base and token URLs rejected for every client, URL syntax in path segments encoded, redirects not followed (including the token mint).
- Each feature builds independently and the full test suite passes (`.github/workflows/ci.yaml`).
- `docs/parity.md` shows no silent behavior change against the consumer code.
- Gateway caller identity: `rejects_a_token_minted_for_another_role` in `crates/gateway/src/auth.rs`, and `crates/gateway/tests/gateway/core.rs` (`a_request_without_its_tier_credential_is_unauthenticated`, `a_service_account_outside_bot_principals_is_forbidden_and_audited`, `a_read_tier_assertion_does_not_open_the_write_tier`, `readers_have_no_mutation_routes`).
- Gateway account binding: `startup_fails_closed_on_another_account_or_an_unreachable_alpaca` and `an_account_id_in_a_request_is_refused` in `crates/gateway/tests/gateway/core.rs`, and `unknown_fields_are_refused` in `crates/gateway/src/config.rs`.
- Gateway credential: `real_money_refuses_every_credential_but_the_kms_key` and `equal_audiences_are_refused` in `crates/gateway/src/config.rs`.
- Gateway destinations and key forms: `a_withdrawal_outside_the_caller_lane_is_refused_before_sending` and `a_journal_to_an_unknown_counterparty_is_refused_before_sending` (`wallet.rs`), `a_mint_outside_the_pinned_recipients_is_refused_on_every_tier` (`tokenization.rs`), `a_key_in_the_other_tier_form_is_refused_before_anything_is_sent` (`orders.rs`), all in `crates/gateway/tests/gateway`, and `bot_withdrawals_are_switched_off_without_pinned_destinations_but_human_ones_are_not` (`crates/gateway/src/handlers/wallet.rs`).
- Gateway audit: `the_bot_reads_its_funds_and_withdrawable_cash_and_each_read_is_audited` and `malformed_input_is_refused_and_audited` (`core.rs`), `each_placement_route_sends_its_alpaca_order_and_is_audited_as_applied` (`orders.rs`), `a_withdrawal_past_its_deadline_answers_outcome_unknown_and_settles_applied`, `a_withdrawal_that_fails_after_its_deadline_settles_outcome_unknown_with_the_status` and `oversized_caller_values_never_grow_an_audit_record` (`wallet.rs`), all in `crates/gateway/tests/gateway`, and `the_audit_keeps_the_first_alpaca_ids_each_cut_at_the_id_cap` (`crates/gateway/src/state.rs`).
- Gateway send gate and deadlines: `a_withdrawal_whose_whitelist_read_outlasts_its_deadline_is_never_sent` and `whitelist_remove_sends_no_delete_once_its_deadline_passed` (`wallet.rs`), and `a_read_past_its_deadline_answers_upstream_transient` and `a_mutation_in_flight_at_shutdown_answers_outcome_unknown_at_once` (`core.rs`), the last of which also holds `run` to the 8 second shutdown grace, all in `crates/gateway/tests/gateway`; `a_mutation_whose_request_the_send_gate_held_back_was_not_applied` (`crates/gateway/src/answer.rs`); and in the library `a_send_gate_holds_back_every_request_after_it_closes` (`src/request_id.rs`) and `a_caller_whose_gate_closed_while_it_waited_on_a_mint_starts_none` (`src/auth.rs`).
- Gateway human budget: `the_human_budget_throttles_humans_and_never_the_bot` (`core.rs`) and `activities_list_reads_ten_pages_for_a_human_and_every_page_for_the_bot` (`account.rs`), both in `crates/gateway/tests/gateway`.
- Gateway profile and issuer: `the_bot_mint_callback_is_applied_and_audited_as_s01`, `a_redeem_rejected_after_a_server_error_is_outcome_unknown_and_alone_not_applied`, `a_bad_issuer_key_symbol_or_quantity_is_refused_before_alpaca`, `a_stream_answer_that_is_not_an_event_stream_keeps_its_alpaca_status`, `the_stream_relays_alpaca_bytes_unchanged_from_the_replay_position`, `humans_cannot_reach_the_issuer_posts_nor_the_s01_bot_orders`, and `a_t0_deployment_serves_none_of_the_issuer_routes` (`issuer.rs` in `crates/gateway/tests/gateway`), and the profile matrix tests in `crates/gateway-api/src/ops.rs`.
- Gateway config errors: `a_malformed_credential_line_stays_out_of_the_error` (`crates/gateway/src/config.rs`).
- The shipped image builds on every pull request (`gateway-oci` job in `.github/workflows/ci.yaml`), and the gateway crates compile with the shipped default features (`gateway` matrix entry).
